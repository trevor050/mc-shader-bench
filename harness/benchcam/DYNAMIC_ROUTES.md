# Deterministic dynamic routes

This client mod runs project-specific shader stress routes in the actual integrated-server world. It does not replace Iris, Sodium or the shader pack and is not a recognized universal benchmark standard. Existing static captures remain useful controls; the dynamic suite separately exercises moving visibility, reflections, lighting, cloud animation and temporal history.

## Clock and camera model

Load one closed route with `route load <base64url-json>`, then call `route start warmup=2 measure=1 arm_ms=5000`. Preparation saves client/server state and positions the spectator at the initial landmark. The response is asynchronous: poll `route status` until terminal. `route cancel` requests restoration. `route clock` exposes JVM monotonic and wall-clock readings for QPC correlation.

Capture clients supply a unique canonical UUID as `request_id=...` on start. Status and terminal receipts echo it, including when the start reply is lost. Automated cleanup uses `route cancel request_id=...`; the render-thread handler refuses a different current request, preventing cancellation of another client's route even if route definitions match. Unscoped cancel remains available for deliberate manual abort.

One scheduled System.nanoTime timeline drives every sample. Translation follows a closed Catmull-Rom curve through a precomputed 1024-subdivision-per-segment arc-length table. Equal elapsed time covers equal distance to table accuracy; yaw and pitch use explicitly unwrapped spline angles. The timeline continues at real-world speed during slow frames and server stalls. Skipped frames therefore skip route positions, rather than earning artificial performance by slowing the camera.

The integrated server updates the real spectator position and chunk center at its tick boundary. Normal LocalPlayer movement packets are suppressed during route ownership. The client samples the same route for every camera update before Minecraft's Camera builds culling matrices and extracts render state. Iris/DH therefore consume the actual moving camera and visibility state, not a post-render screen warp. The player position and inventory selection follow that route too. First-person view, mouse ownership and input are controlled during the run and restored afterward.

The first complete traversal is labeled `streaming`; additional warm traversals are `warmup`. The measured phase begins at a scheduled boundary after those loops, including when no frame lands exactly on that instant. Status/receipts record the schedule, first observed boundary frames, rendered sample counts, frame gaps, server gaps and camera/server distance. Frame gaps and server lag alone never invalidate or remove timings. Separation beyond one chunk during the measured phase explicitly marks `CONTROL_DESYNC_ONE_CHUNK`, because the server chunk center then differs materially from the camera workload. Warm traversal separation is reported without invalidating measured data. Retain raw timing tails even for an invalid control run.

## Changing light and weather

Route environment keyframes control the selected server world clock and the matching client clock. The client clock fields are resolved once from the installed 26.2 API; render samples update primitive fields without adding a time-query mixin to normal gameplay. The server stays authoritative at ticks. Clock targets follow the continuous wall-clock schedule, while native MC 26.2 SUN/MOON environment attributes retain their normal tick sampling and partial-tick interpolation. Minecraft's level and camera attribute caches are deliberately retained. Celestial lighting is therefore tick interpolated, rather than evaluated from the current route clock on every frame; receipts state this limitation explicitly.

Rain and thunder strengths are deterministic client visual overrides, exercising shader fog/wetness/sky/precipitation inputs. Server precipitation and lightning are suppressed, and weather progression is temporarily frozen. This avoids route-induced snow, lightning damage or other weather block edits. It does not benchmark server weather simulation. No inventory item or world block is created, removed or replaced. Natural existing world simulation and unknown-chunk generation cannot be rolled back by this runner; use verified pregenerated landmarks and do not run an unknown route in a valuable world.

World clock alone does not freeze shader animation. Optional installed-Iris TIMER readings record the request, first measured frame, first end frame and finish phase; `-1` means unsupported. Compare these readings when assessing cloud/aurora phase. They do not reset the Iris timer or guarantee that independent shader reloads share a phase.

## State and receipts

Save/restore includes authoritative server position/rotation, game mode, flying flag, velocity, selected slot, exact selected ClockState (including fractional tick/rate/pause), weather flags/timers, current/previous weather interpolation strengths, weather advance gamerule, client camera type/smoothing, HUD and mouse preference. Inventory contents are compared, never overwritten. Preparation rejects occupied shoulders before spectator mode can release parrots, non-self cameras, captured or pending debug frustums, mounted/sleeping/dead players and active item use. Completion and cancellation restore through the server thread and then the client thread. Every independent saved-state group is attempted even if another group fails; failures are aggregated and invalidate the receipt. Disconnect/server-stop hooks restore server state while the integrated server remains available. Forced process termination cannot execute restoration.

MC 26.2 public clock setters discard fractional time, so exact restoration uses the installed private ClockInstance.loadFrom(ClockState) method resolved before server mutation. If the API changes, preparation fails before server mutation. Reflection is version-coupled and must be validated when updating Minecraft. The mod already targets `~26.2`.

Each run writes `minecraft/benchcam/dynamic-routes/<run-id>.json`. The hash covers exact decoded route bytes, while the capture adapter canonicalizes selected JSON before loading. Scheduled monotonic boundaries, terminal reason, exceptions and separate server/client restoration results remain available via `route status`. A route-off client retains only inexpensive active-state checks in its camera/input/player hooks; no route sampling, reflection, serialization or filesystem work runs while inactive.

The installed main-repository GPU profiler, DH/render-distance trials, memory ledger and command capabilities are preserved in this build. Their exact source/jar provenance is recorded in the build packet. Profiler methods return without query submission when recording is off; inactive poll traverses empty queues. This is a source contract, not a measured overhead estimate. Acceptance routes require an idle/closed, drained and error-free profiler, and block profiler start or other state-changing BenchCam commands until route control ends. Profiler span/pass query times remain diagnostics and are not GPU Busy; use PresentMon for acceptance measurements.

## Gates

Dependency-free RouteMathTest verifies constant speed, periodic pose/tangents, deterministic sampling after skipped frames and malformed definitions. DynamicRouteTest validates every shipped catalog route against the actual parser and samples its speed/environment/hash invariants. BestEffortRestoreTest injects failures and verifies that later restore groups still run and the accumulator remains failed. Python protocol/clock/capture tests run separately without Minecraft. These fixtures do not prove live state restoration. A successful Gradle build does not prove mixin application, camera smoothness, restoration or live capture integrity.

After a coordinated build/install/restart, first exercise load/start/status/cancel and normal completion without timing, verify authoritative pose/game mode/time/weather/inventory restoration, then confirm camera/chunk-center motion and route hash. Run the first traversal and warmed route as distinct receipts. Only then perform attested QPC/PresentMon A/B/A captures with full raw frame tails and matching framebuffer, active console renderer and live shader hashes.
